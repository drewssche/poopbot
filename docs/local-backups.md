# Локальные резервные копии и проверка восстановления

Скрипт `scripts/backup_ops.py` запускается **на хосте**, требует Python 3.10+ и Docker.
Внешнее хранилище и CI не используются. Рабочая БД доступна только на чтение;
никакие исправления истории, включая спорные записи, не выполняются.

## Расписание

- Создание копии: ежедневно **03:15 UTC / 06:15 Минск**.
- Проверка последней копии: воскресенье **03:45 UTC / 06:45 Минск**.
- systemd-таймеры с `Persistent=true` запускают пропущенную задачу после включения VPS.
- Общая блокировка исключает одновременное создание, удаление и проверку архивов.

## Что сохраняется и проверяется

Новые архивы: `backups/poopbot_daily_*.dump` в формате PostgreSQL custom и соседний
`.json` с SHA-256 архива, идентификатором образа PostgreSQL, количеством строк и
контрольными суммами **всех 13 таблиц**. Дамп и показатели читаются из одного
экспортированного снимка в транзакции `REPEATABLE READ READ ONLY`, поэтому новые
отметки во время копирования не приводят к ложным расхождениям.

Проверка создаёт временный PostgreSQL 16 в контейнере `poopbot-restore-check-*`:

- сеть отключена, порты не публикуются, рабочий том БД и каталог проекта не подключаются;
- данные находятся только в tmpfs; пределы — 256 МиБ RAM, 0,25 CPU и 128 процессов;
- токен Telegram и конфигурация бота в контейнер не передаются;
- восстановление выполняется одной транзакцией, любая ошибка останавливает проверку;
- контрольные суммы и число строк сравниваются с исходным снимком, проверяется наличие версии миграции;
- контейнер удаляется после успеха и обработанной ошибки.

Успех означает совпадение восстановленных данных со снимком, **а не исправление
исторических несоответствий**. Спорные записи сравниваются наравне с остальными.
Дамп не заменяет копию `.env` и доступов для переноса всего сервера: их следует хранить отдельно.

Поддерживаются прежние `poopbot_*.sql.gz`: gzip проверяется при распаковке, SQL
восстанавливается с остановкой при любой ошибке, все таблицы читаются. У таких
архивов нет исходного манифеста, поэтому результат явно помечается
`legacy_restore_without_manifest`, без заявления о сравнении с исходной БД.

По умолчанию выбирается последняя ежедневная копия. Возраст более 36 часов — ошибка.
Для ручной проверки старого архива можно явно указать его имя. Новые копии требуют
наличия локального образа PostgreSQL, записанного в манифесте; не удаляйте его до
проверки совместимости архивов с заменой образа.

## Хранение и журнал

Хранятся семь последних новых ежедневных архивов и, при необходимости, более
старый последний успешно проверенный архив. Старые SQL.gz и ручные копии перед
выкладками автоматически не удаляются. Удаление старых ежедневных архивов происходит
только после успешного создания новой копии.

В `backups/operations/`:

- `YYYY-MM.jsonl` — начало, результат, длительность, ошибки и результат доставки уведомления;
- `last_create.json`, `last_verify.json` — результат последнего запуска;
- `last_verified.json` — последняя успешная проверка; ошибка его не перезаписывает.

Файлы создаются с доступом только владельцу. В журнале нет строк пользовательских
данных, токенов и паролей. Дополнительный журнал: `journalctl -u poopbot-backup -u poopbot-restore-check`.

Ошибки создания и восстановления отправляются в личку `BOT_OWNER_ID` через
`BOT_TOKEN` из `/opt/poopbot/.env`. Доставка повторяется до трёх раз; неудача также
фиксируется в журнале. Успешные регулярные запуски не отправляют сообщений.
Локальная система не может уведомить о полном отключении VPS или доставить сообщение
при недоступном Telegram. Проверки восстановления не запускают рабочего бота.
Задачи запускаются на хосте даже при неудаче запуска Docker: ошибка Docker также
попадёт в журнал и уведомление, если сам VPS и Telegram доступны.

## Ручной запуск

```bash
cd /opt/poopbot
python3 scripts/backup_ops.py create
python3 scripts/backup_ops.py verify
python3 scripts/backup_ops.py verify --archive poopbot_2026-10-19_03-15-01.sql.gz
python3 scripts/backup_ops.py test-alert
```

Для установки сохранить прежний crontab, убрать **только** старую строку запуска
`/opt/poopbot/backup_db.sh`, установить четыре файла из `deploy/systemd/` в
`/etc/systemd/system/`, выполнить `systemctl daemon-reload` и включить таймеры:

```bash
systemctl enable --now poopbot-backup.timer poopbot-restore-check.timer
systemctl list-timers 'poopbot-*'
```

Рабочие контейнеры перезапускать не нужно. Если проверка была принудительно убита
через SIGKILL или Docker был недоступен во время очистки, проверить наличие контейнера
с префиксом `poopbot-restore-check-` и меткой `poopbot.restore-check=true`; удалять
только этот временный контейнер. Обычный SIGTERM обрабатывается с очисткой.
