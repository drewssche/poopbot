# Недельные карточки

С понедельника после 09:00 по часовому поясу чата планировщик ставит в очередь
отчёт за предыдущие понедельник–воскресенье. Учитываются прежние настройки
включения бота и уведомлений. Месячные и годовые отчёты не меняются.

Недельный отчёт состоит из изображения и полного прежнего текста (при необходимости
текст разбивается на сообщения до лимита Telegram). В личке учитываются только
собственные отметки, сделанные в этой личке; в группе — отметки этой группы.
Обе формы строятся из `poop_events`, с проверкой чата сессии и `origin_chat_id`,
в одной транзакции REPEATABLE READ. Изображение хранит даты отчёта, а не текущей
недели. На картинке показаны до восьми участников; текст сохраняет штатные детали.
Изображение рендерится Pillow вне event loop, без браузера и внешних сервисов.

`/debug → Недельный отчёт` использует тот же путь, в том числе режим превью.
Превью показывает неделю выбранной сессии, поэтому текущая неделя может быть
ещё не завершена. Меню объяснения сохранено на текстовом сообщении.

## Обновления

`weekly_reports` хранит получателя, период, ID сообщений, хеши, версии и повторы.
Триггеры PostgreSQL замечают изменения `poop_events`, включая массовые удаления,
перенос/удаление сессии и восстановления из бота и Mini App. Старые сообщения
заменяются через `editMessageMedia` / `editMessageText`; неизменившееся содержимое
повторно не отправляется. Изменения качества отметки могут менять только текст.
Текст также зависит от предыдущей недели, сравнения с другими группами и стриков:
такие изменения тоже инвалидируют зависимые отчёты. Публикации, удалённые вручную,
автоматически не создаются заново; владелец получает сообщение об ошибке.

Очередь пробуждается через PostgreSQL LISTEN/NOTIFY после commit, без опроса БД
в простое. Один дополнительный DB connection держит LISTEN и advisory lock
единственного издателя. Изменения за 0,75 с объединяются; рендер и SQL выполняются
в рабочем потоке. При рестарте/переподключении проверяются незавершённые задания.
Новая версия, появившаяся во время отправки, остаётся на следующую обработку.

При ошибке применяется задержка 5–300 с (для Telegram 429 — не меньше retry_after),
до восьми попыток. После исчерпания попыток задание сохраняется, владелец получает
уведомление; новая правка возобновляет повторы. Для ручного повтора после устранения
причины можно сбросить attempts/retry_at и увеличить revision выбранной строки.
Нельзя сбрасывать message_id без проверки: это создаст новые сообщения.
Как и у других исходящих сообщений Bot API, при потере ответа после первого
sendPhoto/sendMessage невозможно гарантировать отсутствие дубликата: Telegram
не предоставляет ключ идемпотентности отправки. Подтверждённые ID сохраняются сразу
после каждого ответа; последующие обновления идемпотентны.

Исторические текстовые отчёты не преобразуются и не рассылаются повторно.
Миграция не изменяет отметки. Очередь входит в резервные копии и проверку восстановления;
сохранена проверка архивов до появления этой таблицы.

## Проверка

```sh
.venv/bin/pytest -q
# Только для отдельной пустой базы с выполненным alembic upgrade head:
WEEKLY_REPORT_TEST_DATABASE_URL=postgresql+psycopg://... .venv/bin/pytest -q tests/test_weekly_reports_postgres.py
```

Интеграционный тест требует отсутствия чатов и очищает только свою отдельную БД.
Он проверяет реальные триггеры, откат, прошлый/будущий период, запуск из очереди,
LISTEN и отсутствие запросов в простое. Не использовать рабочую БД.

После выкладки: `docker compose logs bot`, строка `Weekly report listener ready`,
здоровье бота и Mini App, отсутствие накопления заданий. Журнал доставки содержит
только ID/версию и тип ошибки, без содержимого отчёта и токена.

Разовая проверка в Telegram (публикует **только в личку BOT_OWNER_ID**):
`docker compose exec -T bot python -m scripts.preview_weekly_reports --source-chat <group_id> --send-to-owner`.
Три снимка реальных данных читаются из рабочей БД. Четыре демонстрации изменений
используют отдельную SQLite в памяти, включая настоящие вызовы Telegram для
замены изображения/текста. Рабочие отметки и очередь не меняются. Скрипт печатает
ID сообщений и результат; тестовые снимки после завершения больше не обновляются.
