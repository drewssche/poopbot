# Карточки недельных, месячных и годовых отчётов

## Ежедневные вопросы

Новые Q1 из планировщика, восстановления пропущенной публикации, `/start` и
личного диалога отправляются одним фото с текстом вопроса и рабочими кнопками.
Картинка невысокая (840 × 328): логотип, период, семь дней со счётчиками начиная
с 1 и короткий итог. Каждый день получает своё сообщение и привязку
`weekly_reports.q1_session_id`, календарь показывает неделю даты сессии.

Изменения отметок из бота и Mini App обновляют все её дневные картинки этого чата
через прежнюю очередь. В личке Q2/Q3 сохраняют свой экран при обновлении картинки;
при закрытии сессии остаётся кнопка «Забыл отметиться». Изменения только текста
и кнопок не перерисовывают картинку. Название чата для дневной картинки через
Telegram не запрашивается.

Прежние текстовые вопросы сохраняют ID и обычный путь редактирования; они не
заменяются массово при выкладке. Ранее отправленные фото-вопросы при следующем
штатном обновлении получают невысокую картинку в том же сообщении. Подписи
ограничены 1024 символами Telegram по целым строкам без разрыва упоминаний,
с переходом к `/app` для полного списка большой группы.

Для этой смены формата достаточно обновления **bot**: схема БД и протокол Mini App
не меняются. Дополнительных фоновых опросов БД не добавляется.

## Общий кэш карточек

Для сообщений одного чата используется общий кэш изображений: до 32 PNG,
не более 4 МиБ. Ключ учитывает период, все данные карточки, оформление и файлы
шрифтов/иконок. Одновременные запросы одного изображения выполняют одну отрисовку.
Хеш визуальных данных сохраняется вместе с доставленным сообщением: изменение
только подписи или кнопок не запускает Pillow даже после перезапуска/очистки кэша.
Проверка свежих данных и подписей по-прежнему выполняется из одной транзакции.
Изменения количества, участников, периода и оформления дают новый ключ.
Каждое сообщение сохраняет собственную подпись, кнопки, ID и версию доставки.
Для существующих карточек без нового хеша первая обычная обработка заполнит его;
массового обновления при миграции нет.

## Периодические отчёты

С понедельника после 09:00 по часовому поясу чата планировщик ставит в очередь
отчёт за предыдущие понедельник–воскресенье. Учитываются прежние настройки
включения бота и уведомлений. В первый день месяца и года после 09:00 отправляются
такие же карточки за предыдущий полный месяц и год. Если сроки совпали,
каждый период получает отдельное сообщение и ключ доставки.

Каждый отчёт — одно сообщение. Недельный отчёт использует визуальный формат:
календарь, количество отметок, сравнение двух недель полосками, активные дни и
участники, место группы среди чатов и его изменение, тройка участников, распределения
консистенции/самочувствия. Неуказанные ответы считаются отдельно; при отсутствии
ответов показано «Нет ответов», без придуманного распределения. При заполненных
ответах высота блоков увеличивается, чтобы строки не перекрывались.

Внизу — иконки массы и воды с пометкой «примерно»: 150 г и 6 л на отметку.
Это расчётные значения, не измерения. Капля и объём воды окрашены в `#3DA5FF`.
Под ними — шуточное сравнение массы с животным и локальный силуэт; при нуле
отметок блок сравнения скрыт. Размер недельного образца без ответов —
840 × 1124 при наличии отметок, 840 × 992 без отметок.
В личной версии нет группового рейтинга и чужих данных.
Подпись недельного отчёта короткая: название чата и переходы в `/stats` и `/app`.

Месячный и годовой форматы: на картинке календарь, два итога, блоки массы/воды
и сравнение с животным; в подписи сравнение периодов, качество ответов, рейтинг
и оценки. Месяц показывает все 28–31 дней;
год — 12 месяцев в три ряда. Жёлтые счётчики начинаются с 1.
Ориентиры массы и лицензия силуэтов описаны в [report-animals.md](report-animals.md).

Все визуальные данные и подпись строятся из одной транзакции REPEATABLE READ,
с проверкой чата сессии и `origin_chat_id`. Рендер Pillow выполняется вне event loop.
Кэш различает дневной и недельный макеты. Для недельного макета он также учитывает
ответы, прошлую неделю и рейтинг; данные, видимые только в подписи, не вызывают рендер.

Недельный, месячный и годовой отчёты в `/debug` используют тот же путь, в том числе режим превью.
Превью показывает период выбранной сессии, поэтому текущий период может быть
ещё не завершён. Кнопка объяснения находится под карточкой.

## Обновления

`weekly_reports` хранит получателя, тип и границы периода, начало предыдущего
периода, ID сообщения, хеши, версии и повторы. Историческое имя таблицы сохранено;
все три типа обслуживает один обработчик без дополнительных фоновых соединений.
Триггеры PostgreSQL замечают изменения `poop_events`, включая массовые удаления,
перенос/удаление сессии и восстановления из бота и Mini App. Изображение и подпись
заменяются одним `editMessageMedia`. Изменение категории ответа обновляет картинку
недельного отчёта; у месячного и годового — только подпись (`editMessageCaption`).
Дневной календарь при изменении качества не перерисовывается. Неизменившееся содержимое повторно не отправляется.
Отчёт также зависит от предыдущего периода и сравнения с другими группами:
такие изменения тоже инвалидируют зависимые отчёты. Публикации, удалённые вручную,
автоматически не создаются заново. Если пропало именно известное фото-сообщение
в личке, обновления отключаются без уведомления владельца; ошибки в группах
по-прежнему требуют внимания.

Очередь пробуждается через PostgreSQL LISTEN/NOTIFY после commit, без опроса БД
в простое. Один дополнительный DB connection держит LISTEN и advisory lock
единственного издателя. Изменения за 0,75 с объединяются; рендер и SQL выполняются
в рабочем потоке. При рестарте/переподключении проверяются незавершённые задания.
Новая версия, появившаяся во время отправки, остаётся на следующую обработку.
Перед обращением к Telegram издатель повторно проверяет версию после рендера.
Если снимок уже устарел, он не отправляется и не считается доставленным: очередь
готовит свежий. Отключённые за время рендера задания также пропускаются. Это одна
проверка по ID на обработку, без дополнительных запросов в простое. Проверка не
может отменить запрос, уже принятый Telegram; изменения во время самого HTTP-запроса
по-прежнему доставляются следующей обработкой.
После успешного commit кнопки «+»/«−» подтверждают пользователю сохранённое число
его отметок за день, даже если обновление карточки ещё в очереди.

При ошибке применяется задержка 5–300 с (для Telegram 429 — не меньше retry_after),
до восьми попыток. После исчерпания попыток задание сохраняется, владелец получает
уведомление; новая правка возобновляет повторы. Для ручного повтора после устранения
причины можно сбросить attempts/retry_at и увеличить revision выбранной строки.
Нельзя сбрасывать message_id без проверки: это создаст новые сообщения.
Если Telegram запрещает обращение к личному чату получателя (`TelegramForbiddenError`,
например при блокировке бота), задание отключается без уведомления владельца.
В журнале остаются ID задания и тип ошибки без текста ответа Telegram.
То же правило действует при `message to edit not found` во время изменения
подписи или картинки известного сообщения в личке, в том числе при закрытии
ежедневного вопроса. Проверяются метод, получатель и ID фото; чужие сообщения,
ошибки исходной группы, форматирования и другие сбои не подавляются. Сохраняются
отметки и настройки пользователя; отключается только обновление пропавшего поста.
Журнал дополнительно содержит фиксированную категорию причины (`message_missing`,
`access_denied` и т. п.), без содержимого сообщения и полного ответа Telegram.
Запрет доступа к группе, включая исходную группу отчёта для личного предпросмотра,
и остальные технические сбои по-прежнему вызывают уведомление владельцу.
Как и у других исходящих сообщений Bot API, при потере ответа после первого
sendPhoto невозможно гарантировать отсутствие дубликата: Telegram
не предоставляет ключ идемпотентности отправки. Подтверждённые ID сохраняются сразу
после ответа; последующие обновления идемпотентны.

Исторические текстовые отчёты не преобразуются и не рассылаются повторно.
Миграция не изменяет отметки. Очередь входит в резервные копии и проверку восстановления;
сохранена проверка архивов до появления этой таблицы.

## Проверка

```sh
.venv/bin/pytest -q
# Только для отдельной пустой базы с выполненным alembic upgrade head:
WEEKLY_REPORT_TEST_DATABASE_URL=postgresql+psycopg://... .venv/bin/pytest -q tests/test_weekly_reports_postgres.py
```

Интеграционный тест требует отсутствия чатов и очищает только свою отдельную БД.
Он проверяет реальные триггеры, откат, прошлый/будущий период, запуск из очереди,
LISTEN и отсутствие запросов в простое. Не использовать рабочую БД.

После выкладки: `docker compose logs bot`, строка `Calendar report listener ready`,
здоровье бота и Mini App, отсутствие накопления заданий. Журнал доставки содержит
только ID/версию и тип ошибки, без содержимого отчёта и токена.

Разовая проверка в Telegram (публикует **только в личку BOT_OWNER_ID**):
`docker compose exec -T bot python -m scripts.preview_weekly_reports --source-chat <group_id> --send-to-owner`.
Три снимка реальных данных читаются из рабочей БД. Четыре демонстрации изменений
используют отдельную SQLite в памяти, включая настоящие вызовы Telegram для
замены изображения/подписи. Рабочие отметки и очередь не меняются. Скрипт печатает
ID сообщений и результат; тестовые снимки после завершения больше не обновляются.
Для месяца/года добавить `--period month` или `--period year`.
Флаг `--preview-only` отправляет только один снимок текущего периода группы,
без серии демонстраций и без дополнительных текстовых сообщений.

При переходе с первоначального формата из двух сообщений подпись добавляется
к прежней карточке, а связанный текст удаляется по сохранённому ID. Если Telegram
не позволяет удалить слишком старое сообщение, его текст заменяется указателем
на карточку. Для новых отчётов всегда отправляется только одно сообщение.
