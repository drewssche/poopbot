# Карточки недельных, месячных и годовых отчётов

С понедельника после 09:00 по часовому поясу чата планировщик ставит в очередь
отчёт за предыдущие понедельник–воскресенье. Учитываются прежние настройки
включения бота и уведомлений. В первый день месяца и года после 09:00 отправляются
такие же карточки за предыдущий полный месяц и год. Если сроки совпали,
каждый период получает отдельное сообщение и ключ доставки.

Каждый отчёт — одно сообщение: изображение с краткими итогами в подписи
(до 1024 символов Telegram). Подпись содержит период, чат, количество отметок,
сравнение с предыдущим календарным периодом, место группы среди чатов, консистенцию, самочувствие
и оценки объёма/воды. Полная статистика доступна через `/stats` и `/app`.
В личке учитываются только собственные отметки из этой лички; в группе — её отметки.
Изображение и подпись строятся из `poop_events` с проверкой чата сессии и
`origin_chat_id` в одной транзакции REPEATABLE READ. На картинке показаны до восьми
участников; даты всегда соответствуют периоду отчёта. Рендер Pillow выполняется
вне event loop, без браузера и внешних сервисов. Дизайн карточки сохранён.
Неделя показывает семь дней; месяц — календарную сетку всех 28–31 дней;
год — 12 месяцев, сгруппированных в три ряда по четыре. Жёлтые счётчики
на годовой карточке показывают число отметок за месяц. Число дней и сравнения
учитывают високосные годы и разную длину месяцев.

Недельный, месячный и годовой отчёты в `/debug` используют тот же путь, в том числе режим превью.
Превью показывает период выбранной сессии, поэтому текущий период может быть
ещё не завершена. Кнопка объяснения находится под карточкой.

## Обновления

`weekly_reports` хранит получателя, тип и границы периода, начало предыдущего
периода, ID сообщения, хеши, версии и повторы. Историческое имя таблицы сохранено;
все три типа обслуживает один обработчик без дополнительных фоновых соединений.
Триггеры PostgreSQL замечают изменения `poop_events`, включая массовые удаления,
перенос/удаление сессии и восстановления из бота и Mini App. Изображение и подпись
заменяются одним `editMessageMedia`; если изменилось только качество отметки,
используется `editMessageCaption`. Неизменившееся содержимое повторно не отправляется.
Подпись также зависит от предыдущего периода и сравнения с другими группами:
такие изменения тоже инвалидируют зависимые отчёты. Публикации, удалённые вручную,
автоматически не создаются заново; владелец получает сообщение об ошибке.

Очередь пробуждается через PostgreSQL LISTEN/NOTIFY после commit, без опроса БД
в простое. Один дополнительный DB connection держит LISTEN и advisory lock
единственного издателя. Изменения за 0,75 с объединяются; рендер и SQL выполняются
в рабочем потоке. При рестарте/переподключении проверяются незавершённые задания.
Новая версия, появившаяся во время отправки, остаётся на следующую обработку.

При ошибке применяется задержка 5–300 с (для Telegram 429 — не меньше retry_after),
до восьми попыток. После исчерпания попыток задание сохраняется, владелец получает
уведомление; новая правка возобновляет повторы. Для ручного повтора после устранения
причины можно сбросить attempts/retry_at и увеличить revision выбранной строки.
Нельзя сбрасывать message_id без проверки: это создаст новые сообщения.
Как и у других исходящих сообщений Bot API, при потере ответа после первого
sendPhoto невозможно гарантировать отсутствие дубликата: Telegram
не предоставляет ключ идемпотентности отправки. Подтверждённые ID сохраняются сразу
после ответа; последующие обновления идемпотентны.

Исторические текстовые отчёты не преобразуются и не рассылаются повторно.
Миграция не изменяет отметки. Очередь входит в резервные копии и проверку восстановления;
сохранена проверка архивов до появления этой таблицы.

## Проверка

```sh
.venv/bin/pytest -q
# Только для отдельной пустой базы с выполненным alembic upgrade head:
WEEKLY_REPORT_TEST_DATABASE_URL=postgresql+psycopg://... .venv/bin/pytest -q tests/test_weekly_reports_postgres.py
```

Интеграционный тест требует отсутствия чатов и очищает только свою отдельную БД.
Он проверяет реальные триггеры, откат, прошлый/будущий период, запуск из очереди,
LISTEN и отсутствие запросов в простое. Не использовать рабочую БД.

После выкладки: `docker compose logs bot`, строка `Calendar report listener ready`,
здоровье бота и Mini App, отсутствие накопления заданий. Журнал доставки содержит
только ID/версию и тип ошибки, без содержимого отчёта и токена.

Разовая проверка в Telegram (публикует **только в личку BOT_OWNER_ID**):
`docker compose exec -T bot python -m scripts.preview_weekly_reports --source-chat <group_id> --send-to-owner`.
Три снимка реальных данных читаются из рабочей БД. Четыре демонстрации изменений
используют отдельную SQLite в памяти, включая настоящие вызовы Telegram для
замены изображения/подписи. Рабочие отметки и очередь не меняются. Скрипт печатает
ID сообщений и результат; тестовые снимки после завершения больше не обновляются.
Для месяца/года добавить `--period month` или `--period year`.
Флаг `--preview-only` отправляет только один снимок текущего периода группы,
без серии демонстраций и без дополнительных текстовых сообщений.

При переходе с первоначального формата из двух сообщений подпись добавляется
к прежней карточке, а связанный текст удаляется по сохранённому ID. Если Telegram
не позволяет удалить слишком старое сообщение, его текст заменяется указателем
на карточку. Для новых отчётов всегда отправляется только одно сообщение.
